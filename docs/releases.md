# Release procedure

The maintained source is 2n20/creator-tools. Distribution `2n20`, import `twon20` and executable `2n20` retain their identity. Old published artifacts and tags are immutable. The portable skills and canonical Hyperliquid template ship inside both wheel and sdist. Execution dependencies belong to the template's separate requirements-runner.txt.

## Verification

Review dependencies and their licenses before changing either hash lock. Record exact registry file SHA-256 digests and upload timestamps in dependency-review.json. New third-party versions and files must be at least 14 days old. Use local built artifacts during development.

```sh
python3 -m venv .venv
.venv/bin/python -m pip --isolated install --require-hashes --only-binary=:all: -r requirements-release.txt
.venv/bin/python -m pip --isolated install --require-hashes --only-binary=:all: -r src/twon20/templates/hyperliquid-python/requirements-runner.txt
PYTHONPATH=src .venv/bin/python -m unittest discover -s tests -v
cd src/twon20/templates/hyperliquid-python
PYTHONPATH=../../.. ../../../../.venv/bin/python -m unittest discover -s tests -v
cd ../../../..
SOURCE_DATE_EPOCH=1790985600 .venv/bin/python scripts/build_release.py
.venv/bin/python -m pip --isolated install --no-deps dist/*.whl
.venv/bin/python scripts/check_release.py
```

Build twice with the same SOURCE_DATE_EPOCH and compare hashes. Install the sdist separately outside the checkout. Verify consent interoperability, existing setup-directory resume, failure recovery, explicit skill export and installation, conflict preservation, template completeness, generation overwrite refusal, deterministic paper runtime and read-only diagnostics. Check candle recovery, ambiguous child orders, partial fills, restarts, target replacement, deadline/stop cleanup and foreign-account activity with bounded fixtures. Execution tests use mocks/disposable fixtures only. Inspect archive and staged Git paths for secrets, generated state/logs and unrelated material. Do not contact a real wallet or send orders/transfers as a test.

## Trusted Publishing

The setup skill includes `references/step-2.md` and `references/step-3.md`. Preserve the approved instruction text during delivery changes. Release 0.5.0 implements the founder-approved connection-only completion and optional live test, so its reviewed guide changes remove the paper requirement while retaining the two-copy wallet handoff and native questions. `test_setup_guides.py` checks its recorded digests, native question instructions and installed/exported reference files. Any change to these guides needs an explicit behavior review; do not update the digests just to make a delivery change pass.

Configure an existing-project GitHub publisher on PyPI, without an API token:

| Setting | Exact value |
| --- | --- |
| PyPI project | `2n20` |
| GitHub owner | `2n20` |
| Repository | `creator-tools` |
| Workflow filename | `creator-cli-publish.yml` |
| Environment | `creator-cli-pypi` |

The GitHub environment accepts only release tags matching `creator-cli-v*`. Increment the package version, complete review and tests, commit, push and create a new matching immutable tag. Dispatch the workflow against that tag:

```sh
gh workflow run creator-cli-publish.yml --repo 2n20/creator-tools --ref creator-cli-v<VERSION>
```

The SHA-pinned workflow builds/tests artifacts, then gives OIDC permission only to the dedicated publishing job. Verify PyPI's actual version, downloaded file hashes and attestations. Publisher identity must name this repository, workflow, environment, release tag and tested source commit. Attach those exact verified files to the matching GitHub release.

Only then update website installation instructions to the published version and deploy through the application's established process. Retire an obsolete publisher only after the new release is verified. Do not move older tags or delete historical release evidence. TestPyPI is optional and was not used for the initial public-source transition. Record skipped checks separately from passing verification.

## Unreleased

Local builds still identify as 0.5.2 for source verification. They differ from the immutable published 0.5.2 artifacts and must never be uploaded under that version. Choose and bump the next version only in a separately authorized release, with verified anchors from the new deployment. Existing generated projects require regeneration or adaptation. A new deployment requires its own fresh key approval; ordinary withdrawals on that deployment do not.

`status.cashTarget` adds a read-only snapshot in this prepared source. It reports `bps`, `targetAssets` rounded up from current NAV, `actualUnreservedAssets` as the vault's USDC balance less reserved assets, and `allocatableAssets`. Amounts are decimal strings in USDC base units. All five contract reads use one canonical block hash. A stale, unpriced or pending account report, missing getter, reserves exceeding vault cash or changed block leaves the values null with `evidence: unavailable`. Account reports expire after 45 seconds, including time spent on subsequent Hyperliquid reads. The target defaults to 0 and is capped at 5000 bps. It is a target, not guaranteed cash. It does not automatically pull HyperCore margin or increase leverage. This visibility does not add controlled execution or constrain direct Hyperliquid API orders. Setup and retained-key recovery are unchanged.

Discovery requires trading-key version 4. It reads `books(address)`, `keys(address)`, `releases(address)`, `strikes(address)` and `cutsAllowedAt(address)`. `books(address)` returns 16 words: core, phase, stateNonce, reportNonce, observedAt, restrictedAt, restricted, recovered, priced, unpriced, coreAssets, pendingAssets, evmBaseline, exposure, orders, reportHash. Discovery rejects the read unless `unpriced` is at most 511 and names a reason exactly when `priced` is false. A book no report has reached is the exception: its `reportNonce` is 0, `priced` is false and `unpriced` is 0. `releases(address)` returns 10 words: roundAt, need, released, captured, opened, executed, pending, pendingMargin, cancelled, noticeAt. `strikes(address)` returns misses and lastMissAt. `cutsAllowedAt(address)` returns the earliest time a round may reduce positions again. Zero, or a time already passed, means the next round may reduce positions. `RELEASE_NOTICE()` returns 120 and `RELEASE_ROUND()` returns 600. `consentDigest(address,address,uint64,uint64)` is unchanged. Its EIP-712 domain name is `2n20 SDK venue` and its version is `2`. `keys(address)` is unchanged.

`status` reports whether a withdrawal release is active, `noticeAt`, `roundSeconds`, `openedThisRound`, `misses`, `lastMissAt` and `cutsAllowedAt`. `misses` is a count. The key stays approved. The report names each unpriced reason. Before the first valuation report, `pricing.action` is `unreported`. After wind-down, `pricing.next` says that neither the vault nor the service can undo a state only the strategy could. A missing price or an unfinished account read waits for data. During a release, or while no trading key is active, the venue restores standard account mode and withdraws Hyperliquid vault equity after its lockup. Staked HYPE, sub-accounts, borrowing, lending, spot debt, builder-deployed market collateral without a USDC price, and any other unpriced state need the strategy to undo them. For voluntary wind-down, stop new strategy actions, clear outstanding orders and TWAPs, and undo those unsupported states while the key still works. Remove the trading key in the application, wait for confirmed removal, then obtain a fresh full account observation. Submitting removal is not confirmation, and removal does not cancel orders or TWAPs already accepted. The vault refuses irreversible wind-down while authorization is live or pending, orders or TWAPs remain, the report is stale or incomplete, or a strategy-only repair remains. If authorization is already absent, no removal transaction is needed. If removal happened too early, the owner can approve a fresh key while the vault is still active to complete cleanup, then remove it again. This is voluntary shutdown recovery; an ordinary withdrawal never requires reapproval. After wind-down neither the vault nor the service can undo a state only the strategy could. Unverified venue ordering and delayed accepted actions remain release blockers. While the account is unpriced, holders can still cancel the unsettled part of a request and claim settled withdrawals, and holders other than the owner can request withdrawals. Deposits, share transfers, settlement and the owner's withdrawal requests wait. The report includes uncovered assets and key `validUntil`, and it warns when expiry is inside 14 days. During a release the strategy keeps its key and needs no new approval, and the creator can approve a key at most once every 10 minutes. The key stays approved through an ordinary withdrawal. After expiry the creator approves a fresh key. A used key cannot be approved again.

The default withdrawal policy follows Hyperliquid Legacy Vaults: pay from vault cash and free spot USDC first. Native perp margin is used only when the full remaining payment fits while retaining margin for positions at their set leverages. Otherwise the service cancels margin-consuming non-reduce-only orders, smallest estimated margin first, then reduces native positions by 20% per wave until enough collateral is available. Cancellations, reductions and transfers are separate operations with fresh complete observations between them. HIP-3 collateral is a final fallback. The optional owner setting Always proportional instead reduces native perpetual positions by the withdrawing shares’ fraction before settlement. It supports native perps, USDC and a small unheld HYPE gas reserve; other spot holdings or HIP-3 activity require creator portfolio changes before settlement. It is off by default and cannot change while requests are pending.

A release starts after a two-minute notice. Native cuts are capped at 20% of the current position, rounded down, in default mode; each market can be cut at most once per 10-minute round. Proportional mode instead uses the pending request’s share fraction. The service preserves reduce-only orders, uses a 0.4% mark-price limit and observed depth; the contract enforces a 0.5% band. No native minimum-size uplift exceeds the cap. The contract permits at most eight cancellations or five cuts in one round call and relies on the operator to classify protective orders. A full protective book escalates after three distinct fresh observations across 20 minutes, with five-minute rechecks. This bounds silent waiting, not time to payout. Confirmed-revert backoff and gas controls remain; independently safe work can proceed. The creator key stays approved, but a bypassing strategy can reuse freed margin before capture.

The authorized live runtime reads pending demand and remaining capital apart from its trading loop. It holds new risk before restriction begins, cancels only its owned entry child, and preserves reduce-only children. Fresh policy is checked before submission. Signals continue during a hold, but risk-increasing orders wait. Schema v3 adds capitalMultiple and makes targetNotional a hard ceiling. After settlement, unchanged signals resize against remaining capital. Complete observed reductions during a retained withdrawal interval are reconciled separately from owned fills; unexplained activity stays blocked. Existing generated projects need explicit adaptation. See the bundled WITHDRAWALS.md for custom-executor integration and limitations. Use standard account mode. Do not deposit into a Hyperliquid vault, stake HYPE, open a sub-account, borrow, lend, or hold builder-deployed market collateral without a USDC price. Keep at least 0.01 HYPE in the trading account for Core transfer fees. Use client order ids of 2^64 or more. The vault's reduction orders use the operation nonce shifted left by 8 bits, plus the reduction's index in that round. An order under one of those ids counts as that reduction. In the transactions observed so far, none of which mixed orders with transfers, Hyperliquid ran a transaction's actions in order, 5 or 6 L1 blocks after its HyperEVM block (about 0.3 to 0.4 seconds). Hyperliquid documents only that CoreWriter order actions and vault transfers wait a few seconds. It does not document that the actions stay in that order, or that one failed action leaves the later ones running. A reduction can fill while the transfer after it fails. A thin book can leave a reduction unfilled. The package version is unchanged; these source-preview bytes are not the published 0.5.2 release.


`status.pendingWithdrawals` reports fresh public withdrawal demand before a release becomes restricted, including cash-covered requests. `pendingRequestCount`, `escrowedShares`, `owedAssets`, `reservedAssets`, `uncoveredAssets`, `totalAssets` and `remainingAssets` are decimal strings. `remainingAssets` is totalAssets less pending owedAssets, floored at zero. Vault totalAssets already excludes settled reserves; do not subtract reservedAssets again. `owedAssets` is the rounded-up current NAV value of escrowed shares, not a guaranteed payout. Reserved settled claims are separate from that value. The snapshot includes `restricted`, `operationInProgress`, `operationPhase` and its canonical block identity. Reads share one block hash. Missing reads, a changed block or chain evidence older than 45 seconds return `evidence: unavailable` with null values, never zero demand. During an operation, or while valuation is unpriced or stale, the count and reserves remain visible but valuation amounts are null.

Custom Python bots can call `twon20.withdrawals.poll_withdrawal_policy(scope, rpc)` with a previously verified scope containing `vault`, `approvalContract` and `tradingAccount`. It returns a typed policy with `state`, `ready_to_increase`, `reason` and `capital.remaining_usdc`. The lower-level `poll_pending_withdrawals` and starter `Access.pending_withdrawals()` remain available. Policy data must be less than 20 seconds old; unknown valuation, pending requests, restriction or an in-progress operation inhibits new risk. Reads neither load a signer nor authorize orders. This coordination is cooperative: a direct API client can bypass it, and public data cannot make HyperCore settlement atomic.
