# Release procedure

The maintained source is 2n20/creator-tools. Distribution `2n20`, import `twon20` and executable `2n20` retain their identity. Old published artifacts and tags are immutable. The portable skills and canonical Hyperliquid template ship inside both wheel and sdist. Execution dependencies belong to the template's separate requirements-runner.txt.

## Verification

Review dependencies and their licenses before changing either hash lock. Record exact registry file SHA-256 digests and upload timestamps in dependency-review.json. New third-party versions and files must be at least 14 days old. Use local built artifacts during development.

```sh
python3 -m venv .venv
.venv/bin/python -m pip --isolated install --require-hashes --only-binary=:all: -r requirements-release.txt
.venv/bin/python -m pip --isolated install --require-hashes --only-binary=:all: -r src/twon20/templates/hyperliquid-python/requirements-runner.txt
PYTHONPATH=src .venv/bin/python -m unittest discover -s tests -v
cd src/twon20/templates/hyperliquid-python
PYTHONPATH=../../.. ../../../../.venv/bin/python -m unittest discover -s tests -v
cd ../../../..
SOURCE_DATE_EPOCH=1790985600 .venv/bin/python scripts/build_release.py
.venv/bin/python -m pip --isolated install --no-deps dist/*.whl
.venv/bin/python scripts/check_release.py
```

Build twice with the same SOURCE_DATE_EPOCH and compare hashes. Install the sdist separately outside the checkout. Verify consent interoperability, existing setup-directory resume, failure recovery, explicit skill export and installation, conflict preservation, template completeness, generation overwrite refusal, deterministic paper runtime and read-only diagnostics. Check candle recovery, ambiguous child orders, partial fills, restarts, target replacement, deadline/stop cleanup and foreign-account activity with bounded fixtures. Execution tests use mocks/disposable fixtures only. Inspect archive and staged Git paths for secrets, generated state/logs and unrelated material. Do not contact a real wallet or send orders/transfers as a test.

## Trusted Publishing

The setup skill includes `references/step-2.md` and `references/step-3.md`. Preserve the approved instruction text during delivery changes. Release 0.5.0 implements the founder-approved connection-only completion and optional live test, so its reviewed guide changes remove the paper requirement while retaining the two-copy wallet handoff and native questions. `test_setup_guides.py` checks its recorded digests, native question instructions and installed/exported reference files. Any change to these guides needs an explicit behavior review; do not update the digests just to make a delivery change pass.

Configure an existing-project GitHub publisher on PyPI, without an API token:

| Setting | Exact value |
| --- | --- |
| PyPI project | `2n20` |
| GitHub owner | `2n20` |
| Repository | `creator-tools` |
| Workflow filename | `creator-cli-publish.yml` |
| Environment | `creator-cli-pypi` |

The GitHub environment accepts only release tags matching `creator-cli-v*`. Increment the package version, complete review and tests, commit, push and create a new matching immutable tag. Dispatch the workflow against that tag:

```sh
gh workflow run creator-cli-publish.yml --repo 2n20/creator-tools --ref creator-cli-v<VERSION>
```

The SHA-pinned workflow builds/tests artifacts, then gives OIDC permission only to the dedicated publishing job. Verify PyPI's actual version, downloaded file hashes and attestations. Publisher identity must name this repository, workflow, environment, release tag and tested source commit. Attach those exact verified files to the matching GitHub release.

Only then update website installation instructions to the published version and deploy through the application's established process. Retire an obsolete publisher only after the new release is verified. Do not move older tags or delete historical release evidence. TestPyPI is optional and was not used for the initial public-source transition. Record skipped checks separately from passing verification.

## 0.6.5

Discovery batches independent canonical fixed-block calls and code reads, matches every response by its exact ID, and reuses results only for the same parameters/block within one Rpc instance. Latest/canonical block checks still reach the provider. Missing, duplicate, foreign or failed batch responses establish no partial cache. Existing retry budgets remain. The runner keeps account-wide builder checks at its final entry/cancel preflight, while read-only native observations no longer repeat them. Account observation starts at most once per five seconds. Resolved expired and dust targets stop idle polling; a newer closed-bar signal may create a fresh target within the original session. It cannot replay an expired target on the same bar or replace an unresolved child. Strategy, notional/slippage bounds, per-target chase limits and session deadlines are unchanged. Existing projects need reviewed adapter.py, runtime_adapter.py, executor.py and runtime.py updates.

## 0.6.4

Read-only runtime observations no longer repeat complete deployment and key discovery before planning or reconciling a child. The full authority check remains in the final submission preflight after SDK metadata, before signer loading, followed by fresh account/market/withdrawal checks and deadline admission. Cancellation retains its final authority check. Diagnostic snapshots retain their existing verification. Continuous execution now checks initial margin at the freshly read native cross leverage, together with the exchange's side-specific trade capacity, both taker fees and the fixed reserve. Missing/isolated/conflicting leverage evidence refuses new risk. The diagnostic smoke guard remains unlevered. Strategy, budgets, chase lifetime, slippage, key scope and withdrawal policy are unchanged. Existing projects need reviewed adapter.py and runtime_adapter.py updates.

## 0.6.3

The starter reconciles a retained spot-to-perps transfer through the public non-funding ledger. One exact nonce/account/direction/USDC/amount event and matching current balances are required. Its hash and timestamp are retained and reverified. Missing identity, conflicting evidence, truncated responses and unavailable reads preserve the reservation. Resume never resends a transfer. Existing balance-observed journals remain supported and can reconcile with the same command. Human acknowledgement remains available only for unresolved identity. Dependencies, strategy, authority checks, budgets and setup guides are unchanged. Existing generated projects need reviewed adapter.py, execution.py and runner.py updates.

## 0.6.2

Polling withdrawal helpers obtain fresh signed valuation evidence through the public, rate-protected valuation endpoint. They apply it in read-only EVM calls, where the venue verifies the operator signature, vault and current state/key nonces. Canonical demand and reserves remain visible if pricing fails. Report TTL remains 45 seconds; the 20-second policy limit includes read time, and policy also checks report expiry. No signer, transaction, gas or funded checkpoint is needed. Live previews include capital readiness before execution authorization. Existing generated projects need a reviewed runtime.py update for the preview field; installed polling helpers gain the fresh read path on upgrade. Dependencies, keys, configuration, strategy, execution limits and setup guides are unchanged.

## 0.6.1

Adds `pending_withdrawal_usdc(snapshot, now=None, max_age=20)` and `poll_pending_withdrawal_usdc(scope, rpc, now=None)`. These return gross estimated unsettled withdrawals in Decimal USDC, excluding settled reserves, or `None` for unknown evidence. The snapshot converter makes no RPC calls. ## 0.6.0

Published on October 21, 2026 from immutable tag `creator-cli-v0.6.0`, commit `eefcaaee60071b749552ccccc95b674d1bd8f565`. [PyPI files](https://pypi.org/project/2n20/0.6.0/#files) match the reproducible local builds. The CI matrix passed on Python 3.10, 3.12 and 3.13; 147 CLI and 146 starter tests passed, as did installed wheel and source-package checks. The installed CLI verified the live deployment receipt, code hashes, trading-key version and ABI field counts.

Release 0.6.0 requires trading-key version 4 and bundles verified anchors for that deployment. It includes the withdrawal-aware runner, pending-withdrawal policy, optional cash-target reporting and Proportional default described below. The published 0.5.2 artifacts remain immutable. Existing generated projects require regeneration or adaptation. A new deployment requires its own fresh key approval; ordinary withdrawals on that deployment do not.

`status.cashTarget` adds a read-only snapshot in this release. It reports `bps`, `targetAssets` rounded up from current NAV, `actualUnreservedAssets` as the vault's USDC balance less reserved assets, and `allocatableAssets`. Amounts are decimal strings in USDC base units. All five contract reads use one canonical block hash. A stale, unpriced or pending account report, missing getter, reserves exceeding vault cash or changed block leaves the values null with `evidence: unavailable`. Account reports expire after 45 seconds, including time spent on subsequent Hyperliquid reads. The target defaults to 0 and is capped at 5000 bps. It is a target, not guaranteed cash. It does not automatically pull HyperCore margin or increase leverage. This visibility does not add controlled execution or constrain direct Hyperliquid API orders. Setup and retained-key recovery are unchanged.

Discovery requires trading-key version 4. It reads `books(address)`, `keys(address)`, `releases(address)`, `strikes(address)` and `cutsAllowedAt(address)`. `books(address)` returns 16 words: core, phase, stateNonce, reportNonce, observedAt, restrictedAt, restricted, recovered, priced, unpriced, coreAssets, pendingAssets, evmBaseline, exposure, orders, reportHash. Discovery rejects the read unless `unpriced` is at most 511 and names a reason exactly when `priced` is false. A book no report has reached is the exception: its `reportNonce` is 0, `priced` is false and `unpriced` is 0. `releases(address)` returns 10 words: roundAt, need, released, captured, opened, executed, pending, pendingMargin, cancelled, noticeAt. `strikes(address)` returns misses and lastMissAt. `cutsAllowedAt(address)` returns the earliest time a round may reduce positions again. Zero, or a time already passed, means the next round may reduce positions. `RELEASE_NOTICE()` returns 120 and `RELEASE_ROUND()` returns 600. `consentDigest(address,address,uint64,uint64)` is unchanged. Its EIP-712 domain name is `2n20 SDK venue` and its version is `2`. `keys(address)` is unchanged.

`status` reports whether a withdrawal release is active, `noticeAt`, `roundSeconds`, `openedThisRound`, `misses`, `lastMissAt` and `cutsAllowedAt`. `misses` is a count. The key stays approved. The report names each unpriced reason. Before the first valuation report, `pricing.action` is `unreported`. After wind-down, `pricing.next` says that neither the vault nor the service can undo a state only the strategy could. A missing price or an unfinished account read waits for data. During a release, or while no trading key is active, the venue restores standard account mode and withdraws Hyperliquid vault equity after its lockup. Staked HYPE, sub-accounts, borrowing, lending, spot debt, builder-deployed market collateral without a USDC price, and any other unpriced state need the strategy to undo them. For voluntary wind-down, stop new strategy actions, clear outstanding orders and TWAPs, and undo those unsupported states while the key still works. Remove the trading key in the application, wait for confirmed removal, then obtain a fresh full account observation. Submitting removal is not confirmation, and removal does not cancel orders or TWAPs already accepted. The vault refuses irreversible wind-down while authorization is live or pending, orders or TWAPs remain, the report is stale or incomplete, or a strategy-only repair remains. If authorization is already absent, no removal transaction is needed. If removal happened too early, the owner can approve a fresh key while the vault is still active to complete cleanup, then remove it again. This is voluntary shutdown recovery; an ordinary withdrawal never requires reapproval. After wind-down neither the vault nor the service can undo a state only the strategy could. Unverified venue ordering and delayed accepted actions remain release blockers. While the account is unpriced, holders can still cancel the unsettled part of a request and claim settled withdrawals, and holders other than the owner can request withdrawals. Deposits, share transfers, settlement and the owner's withdrawal requests wait. The report includes uncovered assets and key `validUntil`, and it warns when expiry is inside 14 days. During a release the strategy keeps its key and needs no new approval, and the creator can approve a key at most once every 10 minutes. The key stays approved through an ordinary withdrawal. After expiry the creator approves a fresh key. A used key cannot be approved again.

Proportional withdrawals are the default. Before settlement, the service reduces native perpetual positions by the withdrawing shares’ fraction and confirms the frozen reduction targets, including when vault cash covers the request. This aims to preserve similar leverage and liquidation prices, with costs, rounding and concurrent trading affecting the result. Supported portfolios contain native perps, USDC and a small unheld HYPE gas reserve; other spot holdings or HIP-3 activity require portfolio changes before settlement. Creators can choose Margin-first at creation or change the on-chain mode while the vault is open and idle with no pending withdrawals. Margin-first uses vault cash and free spot USDC, then native margin if it covers the full remainder at the set leverages. Otherwise the service cancels margin-consuming non-reduce-only orders, smallest margin first, then repeats bounded 20% native-position waves. It considers supported HIP-3 collateral last. Removing margin without resizing positions can increase actual leverage and move liquidation prices closer. Both modes preserve reduce-only protection and creator trading authorization, use fresh observations between operations and retain execution, gas and retry limits. Direct API clients can bypass bot coordination and delay withdrawals.

A release starts after a two-minute notice. Native cuts are capped at 20% of the current position, rounded down, in margin-first mode; each market can be cut at most once per 10-minute round. Proportional mode instead uses the pending request’s share fraction. The service preserves reduce-only orders, uses a 0.4% mark-price limit and observed depth; the contract enforces a 0.5% band. No native minimum-size uplift exceeds the cap. The contract permits at most eight cancellations or five cuts in one round call and relies on the operator to classify protective orders. A full protective book escalates after three distinct fresh observations across 20 minutes, with five-minute rechecks. This bounds silent waiting, not time to payout. Confirmed-revert backoff and gas controls remain; independently safe work can proceed. The creator key stays approved, but a bypassing strategy can reuse freed margin before capture.

The authorized live runtime reads pending demand and remaining capital apart from its trading loop. It holds new risk before restriction begins, cancels only its owned entry child, and preserves reduce-only children. Fresh policy is checked before submission. Signals continue during a hold, but risk-increasing orders wait. Schema v3 adds capitalMultiple and makes targetNotional a hard ceiling. After settlement, unchanged signals resize against remaining capital. Complete observed reductions during a retained withdrawal interval are reconciled separately from owned fills; unexplained activity stays blocked. Existing generated projects need explicit adaptation. See the bundled WITHDRAWALS.md for custom-executor integration and limitations. Use standard account mode. Do not deposit into a Hyperliquid vault, stake HYPE, open a sub-account, borrow, lend, or hold builder-deployed market collateral without a USDC price. Keep at least 0.01 HYPE in the trading account for Core transfer fees. Use client order ids of 2^64 or more. The vault's reduction orders use the operation nonce shifted left by 8 bits, plus the reduction's index in that round. An order under one of those ids counts as that reduction. In the transactions observed so far, none of which mixed orders with transfers, Hyperliquid ran a transaction's actions in order, 5 or 6 L1 blocks after its HyperEVM block (about 0.3 to 0.4 seconds). Hyperliquid documents only that CoreWriter order actions and vault transfers wait a few seconds. It does not document that the actions stay in that order, or that one failed action leaves the later ones running. A reduction can fill while the transfer after it fails. A thin book can leave a reduction unfilled. This behavior is part of 0.6.0; it is absent from published 0.5.2.


`status.pendingWithdrawals` reports fresh public withdrawal demand before a release becomes restricted, including cash-covered requests. `pendingRequestCount`, `escrowedShares`, `owedAssets`, `reservedAssets`, `uncoveredAssets`, `totalAssets` and `remainingAssets` are decimal strings. `remainingAssets` is totalAssets less pending owedAssets, floored at zero. Vault totalAssets already excludes settled reserves; do not subtract reservedAssets again. `owedAssets` is the rounded-up current NAV value of escrowed shares, not a guaranteed payout. Reserved settled claims are separate from that value. The snapshot includes `restricted`, `operationInProgress`, `operationPhase` and its canonical block identity. Reads share one block hash. Missing reads, a changed block or chain evidence older than 45 seconds return `evidence: unavailable` with null values, never zero demand. During an operation, or while valuation is unpriced or stale, the count and reserves remain visible but valuation amounts are null.

Custom Python bots can call `twon20.withdrawals.poll_withdrawal_policy(scope, rpc)` with a previously verified scope containing `vault`, `approvalContract` and `tradingAccount`. It returns a typed policy with `state`, `ready_to_increase`, `reason` and `capital.remaining_usdc`. The lower-level `poll_pending_withdrawals` and starter `Access.pending_withdrawals()` remain available. Policy data must be less than 20 seconds old; unknown valuation, pending requests, restriction or an in-progress operation inhibits new risk. Reads neither load a signer nor authorize orders. This coordination is cooperative: a direct API client can bypass it, and public data cannot make HyperCore settlement atomic.
